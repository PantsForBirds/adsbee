# adsbee_1421 firmware — build guide

## Overview

`adsbee_1421` is the firmware for the ADSBee m1421 board, which runs on a TI **CC1314R10**
(SimpleLink CC13x4, Cortex-M33) paired with a Semtech LR2021 radio. It is built entirely inside
the **`ti-lpf2`** Docker container defined in [`compose.yml`](compose.yml) — that container
carries the ARM GCC toolchain and the TI SimpleLink Low Power F2 SDK. There is no need (and no
supported path) to install the toolchain on the host.

Applications in this directory:

- [`ti/`](ti/) — the CC1314R10 application itself.
- [`programmer/`](programmer/) — an RP2040-Zero flash/passthrough jig that bakes the `ti`
  Release hex into its own image (built in the `pico-docker` container).

Shared C++ code comes from [`../common/`](../common/) and [`../modules/`](../modules/) (cppAT),
referenced via the `ADSBEE_COMMON_DIR` / `ADSBEE_MODULES_DIR` CMake variables whose defaults
resolve within this repo both on the host and in the containers.

## Prerequisites

- Docker with the `docker compose` plugin.
- The `coolnamesalltaken/ti-lpf2:latest` image. It is pulled automatically on first run. It is
  an `linux/amd64` image; on Apple Silicon / arm64 hosts it runs under emulation (slower but
  works). The programmer additionally uses `coolnamesalltaken/pico-docker:latest`.

## Quick start

From this `firmware/adsbee_1421/` directory (or via the dispatcher:
`bash firmware/build.sh adsbee_1421 [args...]` from the repo root):

```bash
./build.sh               # build the CC1314 app (ti) in Release
./build.sh -d            # build ti in Debug
./build.sh programmer    # build the RP2040 flashing jig (requires ti built first)
./build.sh build_and_flash  # build ti + programmer, then reflash an attached m1421 via the jig
                         # (prompts to put the jig in BOOT mode, copies the uf2, monitors)
./build.sh flash         # same, but no build steps: flashes the programmer uf2 already on disk
                         # (warns if it is older than the sources or than the baked-in ti hex)
./build.sh clean ti      # remove ti/build
```

Artifacts land in `<app>/build/<Config>/` (see [Build outputs](#build-outputs)).

## Manual build (what the script does)

If you'd rather not use `build.sh`, run the same steps yourself. **`docker compose` must be run
from this `firmware/adsbee_1421/` directory** (where `compose.yml` lives):

```bash
# Start (or reuse) the toolchain container.
docker compose up -d ti-lpf2

# Configure + build. Swap Release for Debug as needed.
docker compose exec ti-lpf2 bash -c "
    set -e
    cd /firmware/adsbee_1421/ti &&
    mkdir -p build/Release && cd build/Release &&
    cmake -DCMAKE_BUILD_TYPE=Release \
          -DCMAKE_C_COMPILER=/usr/bin/arm-none-eabi-gcc \
          -DCMAKE_CXX_COMPILER=/usr/bin/arm-none-eabi-g++ ../.. &&
    cmake --build . --config Release --target all -j \$(nproc)
"
```

To get an interactive shell in the container: `docker compose exec ti-lpf2 bash`.

## Why builds must run in the container

The CMake cache stores **absolute container paths**, e.g.
`CMAKE_HOME_DIRECTORY:INTERNAL=/firmware/adsbee_1421/ti`. If you try to run `cmake`
against the same build directory from the host, CMake aborts with:

```
CMake Error: The current CMakeCache.txt directory .../build/Debug is different than the
directory /firmware/adsbee_1421/ti/build/Debug where CMakeCache.txt was created.
```

So always configure and build from inside the container. (Editing source on the host is
fine — the source tree is bind-mounted into the container.)

## Build outputs

In `ti/build/<Config>/`:

| File               | Description                                              |
| ------------------ | -------------------------------------------------------- |
| `adsbee_1421.elf`  | Linked executable (used for debugging / GDB).            |
| `adsbee_1421.hex`  | Intel HEX image for flashing (generated by default).     |
| `adsbee_1421.map`  | Linker map (symbol/section sizes).                       |
| `adsbee_1421-<version>.hex` / `.elf` / `.map` | Version-stamped copies for release/CI (e.g. `adsbee_1421-0.3.6.hex`); version is parsed from `object_dictionary.cpp`. |

In `programmer/build/<Config>/`: `adsbee_1421_programmer.uf2` (drag-and-drop onto the
RP2040-Zero over BOOT) with the `ti` Release hex baked in, plus version-stamped copies
`adsbee_1421_programmer-fw<version>.uf2` / `.elf` — the `fw` prefix marks the version as that of
the **baked firmware** (the programmer has no version of its own), matching the names CI publishes.

## Version management

`adsbee_1421` carries its own firmware version
([`ti/object_dictionary/object_dictionary.cpp`](ti/object_dictionary/object_dictionary.cpp),
`kFirmwareVersion*`) and settings version
([`ti/settings/settings.hh`](ti/settings/settings.hh), `kSettingsVersion`), independent of
adsbee_1090's. Any change under `firmware/adsbee_1421/` or the shared `firmware/common/` must be
paired with an adsbee_1421 firmware version bump — enforced by
[`../scripts/check_version_sync.sh`](../scripts/check_version_sync.sh), which `build.sh` runs
before every build (as a warning only — it never blocks the build) and which the repo pre-commit
hook runs on every commit (where it does block). Note that a
`firmware/common/` change requires bumping **both** products' versions.

## Flashing

Flash a CC1314R10 over JTAG with a Segger J-Link (see
[`ti/README.md`](ti/README.md) for the GUI flow):

```bash
# Start a J-Link GDB server targeting the CC1314R10.
../scripts/jlink/open_cc1314_jlink.bash
```

Then load `ti/build/<Config>/adsbee_1421.hex` (or `.elf`) via GDB or the J-Link tools.

> The firmware also supports entering the CC1314 ROM UART bootloader for serial reflashing —
> see the `AT+BOOT_UART_BOOTLOADER` command, the [`programmer/`](programmer/) jig, and the
> [`software/adsbee_1421_flasher`](../../software/adsbee_1421_flasher/) host tool.

## SYNC low-power sleep

An external host can force the CC1314 into **STANDBY** (deep sleep, SRAM retained) by driving the
**SYNC line (DIO_5)** HIGH; driving it LOW wakes the MCU. The super-loop in
[`main.cpp`](ti/main.cpp) polls SYNC at the top of each iteration and, when
asserted, calls `SubGHzRadio::Suspend()` and `CommsManager::Suspend()` (release the RF core's and
the console UART's STANDBY power constraints), then `ADSBee::EnterSyncSleep()`, which powers the
LR2021 down, **tri-states the shared LR2021 bus** (`LR2021::TristateInterface()` — see below), arms
SYNC as a falling-edge wake source, enters STANDBY via `PowerCC26XX_standbyPolicy()`, and on wake
restores the bus (`RestoreInterface()`) and re-runs `ApplyReceiverConfig()` to re-initialize the
LR2021 before `CommsManager::Resume()` / `SubGHzRadio::Resume()` restart the console and UAT RX.

> **LR2021 bus handoff:** during sleep the CC1314 releases every LR2021 interface pin it normally
> drives (`LR_CS`, `LR_RESET`, `COPRO_SPI_SCLK`, `COPRO_SPI_PICO`) to high-impedance inputs (with
> idle-state pulls: CS up, the rest down) so an **external MCU can take control of the LR2021**.
> **Host timing contract:** the external MCU must stop driving the LR2021 bus before/as it lowers
> SYNC — the CC1314 re-drives `LR_CS`/`LR_RESET` and re-muxes the SPI pins as soon as it wakes, so
> overlapping drive would cause bus contention.

> **SYNC pull-down note:** SYNC/DIO_5 is configured with an internal **pull-down** (fail-safe: a
> floating/disconnected host reads LOW = the device stays awake). This is **redundant with the
> external 120 kΩ pull present on ADSBee m1421 PCBA Rev D and later and draws extra power** — it is
> retained only to protect earlier PCBAs. The setting lives in
> [`adsbee_1421.syscfg`](ti/syscfg/adsbee_1421.syscfg) (`GPIO7.pull`) and the
> generated `ti_drivers_config.c`; keep the two in sync.

## Repo ↔ container layout

`compose.yml` bind-mounts the host tree into the container, which is why the CMake
`ADSBEE_COMMON_DIR` / `ADSBEE_MODULES_DIR` defaults resolve correctly without overrides:

| Host                          | Container                 |
| ----------------------------- | ------------------------- |
| `firmware/adsbee_1421/`       | `/firmware/adsbee_1421`   |
| `firmware/common/`            | `/firmware/common`        |
| `firmware/modules/`           | `/firmware/modules`       |

The `pico-docker` service mounts `firmware/adsbee_1421/` at the same `/firmware/adsbee_1421`
path (the programmer reads `../ti/build/Release/adsbee_1421.hex` relative to itself), so build
paths are identical whichever toolchain container an app uses.
